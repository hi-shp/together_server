# 운영 안내

## 게시 확인과 보강

`POST_VALIDATION_MODE=enabled`이면 게시 전 제목의 빈 문자·깨진 문자와 명백한 개인 판매·홍보 내용을 확인합니다. GPT 분류를 거친 공지는 그 응답에 들어 있는 공지 여부도 함께 확인합니다. 이 검사를 위한 GPT 호출은 따로 추가하지 않습니다.

게시 후에는 실제 글 화면을 다시 열어 제목, 본문, 원문 링크와 첨부파일을 대조합니다. 제목과 본문은 한 차례 복구를 시도하고, 결과가 불확실하면 게시 주소를 남겨 확인 대상으로 보관합니다. 같은 원문을 다시 처리할 때 이 주소를 사용해 중복 게시를 줄입니다. 첨부파일이 큰 경우에는 내려받기 한도 안에서 파일명을 대조하며, 내용 해시까지 확인한 경우와 구분해 기록합니다.

본문에 들어 있는 숨김 설정과 실행 코드를 정리하고, 상대 링크는 원문 주소를 기준으로 바꿉니다. 글자가 표시되는지와 이미지 로딩 여부를 확인하지만, 이미지 속 글자의 의미나 모든 글꼴의 표시 상태까지 판별하는 검사는 아닙니다. 의심 공지는 `.runtime/quarantine/`에 최대 1,000건 보관합니다. 소수의 검토 대상은 기록으로 남기고, 한 시간에 5건 이상 발생하면 주요 장애로 알립니다.

보강은 프로그램이 직접 게시하고 등록한 글부터 적용합니다. 제목·본문을 바꿔도 기존 첨부파일을 유지하며 새 파일을 합칩니다. 관리자가 직접 수정한 흔적이 있으면 현재 상태를 먼저 확인합니다. 자세한 선정 기준은 [공지 처리 안내](notice-intelligence.md)에 정리했습니다.

## 첨부파일과 디스크

중요 공지에서 받은 첨부파일은 `.runtime/attachments/`에 최근 확인 시점부터 7일간 보관합니다. 내용이 같은 파일은 하나로 저장합니다.

| 설정 | 기본값 | 역할 |
|---|---:|---|
| `ATTACHMENT_CACHE_GB` | 10 | 보관 상한, GiB 기준 |
| `ATTACHMENT_MIN_FREE_GB` | 5 | 새 보관 파일을 만들 때 남겨 둘 공간 |

기간이나 용량을 넘으면 오래된 보관본부터 정리합니다. 따라서 10GiB에 먼저 도달하면 7일보다 빨리 정리될 수 있습니다. 이미 PLATO 글에 올라간 첨부파일은 서버 보관본과 별개로 유지됩니다. 다운로드는 파일을 나눠 받아 메모리 사용을 줄이고, 임시 파일을 완성한 뒤 이름을 확정합니다.

Chrome 작업 폴더는 실행별로 분리해 종료할 때 정리합니다. 비정상 종료로 남은 전용 폴더는 하루 뒤 정리 대상이 됩니다. 프로그램 로그는 터미널 전체 출력을 기록하고 기존처럼 7일간 보관합니다. 사이클이 끝나면 Full Log Bot 채널에 원문 파일을 전송합니다. 파일 길이에 따라 뒤쪽 출력을 잘라내지 않습니다.

## 쪽지와 이메일

기본 `PLATO_NOTIFICATION_TRANSPORT=http`는 로그인한 PLATO 세션으로 발송 화면의 양식과 토큰을 읽어 같은 서버에 요청합니다. 신청자 CSV와 학과별 선택 기준을 그대로 사용합니다. 수신자는 이름과 학번 또는 이메일로 대조하고, 공지별로 확인된 전체 수신자를 한 번의 요청에 담아 전송합니다. 수신자 목록이 크게 달라지면 발송을 보류합니다.

쪽지는 서버의 전송 완료 응답과 인원수를 확인합니다. `PLATO_EMAIL_MODE=queue`이면 이메일 요청은 대기열에 저장하고 크롤러는 다음 공지를 처리합니다. 별도의 `together-email.service`가 독립된 PLATO 로그인 세션으로 발송하고, 발송 전후 내역의 제목과 수신 학번을 대조합니다. 계정은 기존 `.env`의 값을 사용합니다.

이메일 작업자는 수신자 수에 따라 응답을 10분에서 최대 1시간까지 기다립니다. 이 대기는 다른 공지 처리나 새 이메일 요청을 막지 않습니다. 응답이 끊겨도 새 발송 내역에서 같은 제목과 수신자가 확인되면 완료 기록을 복구합니다. 크롤러가 재시작돼도 대기열은 이어서 처리합니다. 이메일 전송 과정은 GPT를 호출하지 않습니다.

터미널과 Discord의 `이메일 전송 완료`는 기존 문구를 유지한 표시로, 대기열 방식에서는 수신자 대조를 마친 요청을 저장했다는 뜻입니다. 실제 발송 확인은 별도 작업자의 기록에서 확인합니다. 늦은 발송 결과가 다음 공지의 터미널 출력 사이에 끼어들지 않도록 두 작업의 출력을 분리했습니다. ‘해당없음’ 공지의 Discord 공지·전송 완료 알림은 생략합니다. 운영 장애 알림은 계속 보냅니다. 이메일은 `PLATO_EMAIL_CONCURRENCY=1`을 기본으로 요청 순서를 지킵니다. 앞선 요청이 지연되거나 결과를 확인 중이면 뒤의 요청이 추월하지 않습니다. 수신자 목록을 함께 사용하고 요청별 로그인 연결과 학교 발송 내역을 대조합니다. 크롤러의 공지 수집과 쪽지 전송은 계속 진행됩니다. `0`은 순서보다 동시 처리를 우선할 때 선택하는 설정입니다. 종료 요청을 받으면 발송 중인 요청의 응답을 기다린 뒤 종료합니다. 이메일은 PLATO 서버에서 수신자별로 발송하여 68명에 약 6분이 걸린 사례가 있습니다. 오래된 대기 요청이 있어도 최근 30분 안에 발송이 진행됐다면 장애로 알리지 않습니다.

전송 결과는 `.runtime/notification-deliveries.sqlite3`에 수신자별로 보관합니다. 신청자 순서나 전송 단위가 바뀌어도 완료된 수신자는 이력을 이어 사용합니다. 이전의 100명 단위 기록도 연결합니다. 끝내 확인할 수 있는 발송 내역이 없으면 확인 대상으로 남기고 재전송을 보류합니다.

`PLATO_NOTIFICATION_TRANSPORT=ui`로 기존 화면 방식을 선택할 수도 있습니다. 운영 중 전송 방식이나 수신자 목록을 바꿀 때는 미확인 전송부터 확인하세요. PLATO의 발송 접수와 받는 편지함 도착은 별도 단계입니다.

서버 적용 스크립트는 이메일 작업자를 함께 등록합니다. 직접 구성하는 환경에서는 별도 터미널에서 `python3 -m together.operations.email_worker`를 실행할 수 있습니다. `PLATO_EMAIL_MODE=direct`는 기존처럼 크롤러가 이메일 발송 결과를 직접 확인하는 방식입니다.

`screen` 안에서 `python3 run_main.py`를 실행하고 `Ctrl+A`, `D`로 분리해도 진행 상황은 같은 세션에 남습니다. 이메일 작업자는 별도 서비스로 실행됩니다. 크롤러를 `Ctrl+C`로 종료해도 이미 대기열에 저장한 이메일은 작업자가 마무리합니다. 발송 작업까지 중지할 때는 `sudo systemctl stop together-email.service`를 사용합니다.

## API 사용량과 비용

`.runtime/api-usage.sqlite3`에 API 응답의 입력·출력·캐시 토큰과 단가 기준 예상 비용을 기록합니다. 운영 호출과 검증 호출을 구분합니다. 같은 모델에 보낸 동일 분류 요청은 7일, 동일 중복 판단 요청은 1시간 동안 재사용합니다. 모델이나 입력 내용이 바뀌면 다시 판단합니다.

`GPT_DAILY_BUDGET_USD`의 기본값은 하루 $0.25입니다. 한국 시간 기준 누적 예상 비용에 $0.005의 여유분을 더해 다음 호출 가능 여부를 판단합니다. 한도 도달 시 API 판단을 보류하고 주요 장애로 알립니다. 실제 청구 상한은 응답 크기, 재시도와 이 프로그램 밖의 사용량에 따라 달라질 수 있습니다.

2026-10-26 확인 단가이며, 백만 토큰 기준입니다.

| 모델 | 입력 | 출력 |
|---|---:|---:|
| GPT-3.5 Turbo | $0.50 | $1.50 |
| GPT-5.4 mini | $0.75 | $4.50 |

같은 토큰 수라면 입력은 1.5배, 출력은 3배입니다. 호출 수와 프롬프트 길이도 비용에 영향을 줍니다. 현재 5.4 mini는 `reasoning_effort=none`, 응답 상한 500토큰으로 설정했습니다. GPT-3.5 Turbo는 2026-10-23에 종료됐습니다. 단가는 [3.5 Turbo 안내](https://developers.openai.com/api/docs/models/gpt-3.5-turbo), [5.4 mini 안내](https://developers.openai.com/api/docs/models/gpt-5.4-mini)를 기준으로 합니다.

계정의 실제 잔액·크레딧 만료일은 결제 화면에서 확인합니다. 일반 API 키만으로 계정 잔액을 실시간으로 읽을 수 있는 것으로 가정하지 않습니다. 운영자가 확인한 정보를 비공개 `.runtime/health/api-budget.json`에 보관하면, 이후 기록된 비용을 차감한 추정치를 계산합니다. 다른 프로그램의 사용량과 가격 변경은 별도 확인이 필요합니다. 실제 운영 표본이 3일 이상 쌓인 뒤 최근 7일 사용량으로 소진 시점을 추정합니다. API 키 만료일과 크레딧 만료일도 구분합니다.

## 주요 장애 감시

`together-health.timer`가 서버에서 10분마다 확인합니다. 주요 기준은 여유 공간 2GiB 미만, 크롤러 중지·정체·연속 실패, 대규모 수집 오류, 지속되는 메모리 부족, 미확인 게시·대량 전송, API 인증·잔액·한도 문제와 크레딧 만료 임박입니다. 예상 운영 여부는 `OPERATIONS_EXPECT_CRAWLER`와 실행 상태 기록으로 판단합니다. 점검 때문에 의도적으로 멈춘 상태는 일반 대기로 처리합니다.

결과는 `.runtime/health/status.json`에 저장하고, 새 주요 장애는 기존 Discord 웹훅으로 알립니다. 같은 장애는 24시간 간격으로 제한합니다. 소규모 링크 오류나 단발성 메모리 상승은 기록으로 확인합니다.

이메일은 별도로 연결한 감시 작업이 `ALERT_EMAIL_TO`로 보내도록 구성할 수 있습니다. 현재 설치의 Codex 감시는 사용자 설정에 따라 주 1회 확인하며, 로컬 컴퓨터와 연결된 메일 서비스가 사용 가능한 동안 동작합니다. 따라서 이메일 확인은 최대 일주일 늦어질 수 있습니다. 서버에서 상시 이메일을 보내려면 별도의 발신 계정 인증이 필요합니다. 서버의 10분 점검과 Discord 감시는 로컬 컴퓨터와 독립적으로 동작하며 GPT를 호출하지 않습니다.

```bash
cd /home/ubuntu/together/Source
python3 tools/health_check.py --json
systemctl status together-health.timer --no-pager
systemctl status together-crawler.service --no-pager
```

실행을 재개할 때는 최근 검증 결과와 미확인 전송을 확인한 뒤 `sudo systemctl enable --now together-crawler.service`를 사용합니다. 설정과 실행 이력에는 계정 정보가 들어갈 수 있으므로 `.env`와 `.runtime/`은 서버 안에서 관리합니다.


## 진행 로그와 개선용 자료

터미널은 게시판 번호·링크와 기존 공지 처리 문구를 유지합니다. 중복·분류 결과의 괄호 안에는 판단 근거를 표시합니다. 분석 기록에는 시간·단계·공지 ID를 함께 남겨 같은 공지의 수집부터 발송까지 대조할 수 있습니다. 문자열 유사도는 정답 확률과 구분해 표시하며 실제 판정 방식과 비교 후보도 기록합니다. 실패한 첨부는 원문 주소와 오류 종류로 추적합니다.

`.runtime/telemetry/`에는 다음 자료를 JSONL로 보관합니다.

- 수집 시각, 실행 코드 버전, 원문 주소와 공지 ID
- 분류 결과와 판단 방식, 로컬 모델 점수
- 중복 결과와 비교 후보 최대 3개, 문자열 유사도
- 첨부파일 이름·크기·내용 해시와 저장 결과
- 게시 확인, 알림 요청·발송 확인 인원, 작업 시간과 실패 종류

파일당 8MiB, 전체 약 256MiB, 최대 90일을 기준으로 정리합니다. 용량 한도에 먼저 도달하면 오래된 기록부터 지워집니다. 기록 저장에 실패해도 공지 처리는 이어갑니다. 구독자 명단과 발송 본문은 이 분석 기록에 넣지 않으며, 이메일 주소·비밀 키·웹훅과 인증용 주소 항목을 가립니다. 분석 기록은 Discord에 파일로 올리는 일반 진행 로그와 별도로 서버 안에 보관합니다.

```bash
python3 tools/review_logs.py --errors --tail 30
python3 tools/review_logs.py --notice-id 공지ID --tail 100
python3 tools/review_logs.py --tail 1000 --export review-events.jsonl
journalctl -u together-email.service -n 50 --no-pager
```

분류 모델을 개선할 때 가장 가치 있는 추가 자료는 잘못 판단한 공지의 정답입니다. 공지 ID·올바른 카테고리·같은 행사인 원문 ID·다른 회차인 이유를 함께 모으면 기준을 실제 사례로 평가할 수 있습니다. 제목만 남은 옛 자료와 달리, 기존 관측 DB에는 최근 10,000건의 본문 앞부분 최대 6,000자와 원문 메타데이터가 있습니다. 내용 전체를 복원할 수 있는 자료와 구분해 사용합니다.

운영 자료를 백업할 때는 `pages.csv`, `titles.txt`, `sorted_labeled_data.csv`, `yesterday.txt`, `.runtime/intelligence/`, 전송 이력 DB와 이메일 대기열을 함께 보관합니다. 모델을 새로 학습하기 전에는 기존 모델 파일과 해당 코드 버전도 별도로 남깁니다. `.env`와 전송 DB에는 인증·수신자 정보가 있으므로 서버의 비공개 백업에 보관합니다.

첨부 이름이 비어 있으면 응답의 파일명 헤더와 주소를 확인하고, 끝내 이름이 없으면 고유한 이름을 만듭니다. `(양식)` 같은 앞부분 괄호는 보존하며 파일 용량을 나타내는 마지막 괄호만 정리합니다. 제어문자, 경로 구분자, 예약 이름, 긴 UTF-8 이름과 동일 이름의 다른 파일도 처리합니다.


대학 공지는 원래의 번호·제목 기준과 기록 순서를 사용합니다. 날짜·updater·첫 CSV 읽기 뒤 브라우저를 만들고, 참여자와 설문을 확인한 다음 대학 공지 기준을 갱신하고 CSV를 다시 읽습니다. `yesterday.txt` 첫째 줄의 일반 공지 제목으로 순번을 맞추고, 일반 글은 저장 번호보다 큰 경우에만 새 공지로 처리합니다. 고정 글은 둘째 줄의 제목·최근 제목·idx 경계를 원본 순서대로 확인합니다. 게시 후 분류를 저장하고, 최근 제목 확인·title 저장·쪽지·메일 등록을 거친 뒤 해당 게시판 번호를 저장합니다. 뒤의 학과에서 실패해도 이미 끝난 대학 공지의 기록을 되돌리지 않습니다. 게시 주소와 발송 기록은 재시작 시 같은 요청이 반복되는 것을 확인하는 용도로 사용하며, 대학 공지의 번호 기준을 우회하지 않습니다.

학교 게시판 조회는 연결을 재사용하며 같은 서버에는 2초 간격을 둡니다. 서로 다른 학과 주소가 같은 서버를 사용하는 경우도 함께 조절합니다. 일시적인 연결 오류는 다시 조회하고, 수집하지 못한 게시판의 기존 공지 번호는 보존합니다.

밀린 공지가 많아도 진행 출력이 이어지면 사이클을 계속 실행합니다. 전체 실행 시간이나 무출력 시간을 이유로 사이클을 종료하지 않습니다. 현재 사이클의 게시판 점검 수는 조회할 때마다 갱신합니다. Discord 전송 결과와 응답 메시지 ID는 서버 분석 기록에 남기며 터미널의 공지 처리 문구는 그대로 표시합니다.

현장실습 학생 모집, 봉사단 참가자 모집, 설문 응답과 의견 수렴은 참여 역할을 먼저 확인합니다. 고사 진행요원은 본문에 수당·시급 조건이 있을 때 취업 정보로 분류합니다. 기존 게시글을 보강할 때는 원래 게시판을 유지하므로 과거에 잘못 분류된 글은 별도 검토가 필요합니다.

밤 12시부터 오전 6시까지 다음 사이클 시작을 기다립니다. 실행 중인 사이클은 끝까지 처리하고 다음 시작 시각을 판단합니다. 검증 감시는 사이클 실패를 기록하며 자동 재접속·재실행을 유지합니다. 개별 사이트 요청의 연결·응답 제한은 계속 적용합니다.

자동 보강의 저장 결과가 검증을 통과하지 못하면 기존 글로 복구합니다. 제목·본문·첨부 전체의 복구를 확인한 건은 해당 보강을 검토 대상으로 남기고 다음 공지를 이어 처리합니다. 복구 결과를 확인할 수 없는 경우에는 처리를 중단합니다. 저장 전후의 차이는 서버의 비공개 보강 백업에 남깁니다.


## 별표 정리와 복구한 게시판

학교의 제목 검색에서 `⭐`가 붙은 글의 모든 결과 페이지를 먼저 읽습니다. 별표가 없는 페이지가 나오더라도 탐색을 중단하지 않습니다. 오늘 이전 글의 제목에서 별표만 제거하며, 본문·첨부 목록·고정 상태가 유지되는지 다시 확인합니다. 실제 탐색한 페이지와 수정 백업은 서버에 남깁니다.

삭제된 게시판은 공식 새 주소와 실제 목록이 확인된 경우에만 복구합니다. `ops/restore_boards.py`는 기존 CSV의 학과명·주소·숫자를 그대로 두고 확인된 새 행만 한 번 추가합니다. 독어독문학과 대학원과 AI융합교육전공 게시판을 확인했으며, 과거 글이 한꺼번에 발송되지 않도록 복구 시점의 최신 번호를 기준으로 시작합니다. AI융합교육전공은 기존 교육혁신/AI 구독 학과명으로 연결하며 교육혁신전공의 별도 게시판은 확인되지 않았습니다. 학교가 메뉴를 삭제하거나 모듈을 중단한 경우에는 그 상태를 표시하고 번호를 보존합니다.

함수별 원본 대조는 [레거시 동작 대조](legacy-compatibility.md)에 정리했습니다.

별표 작업에서는 큰 원문 이미지를 화면에 표시하는 대신 제목·본문 HTML·첨부 목록을 대조합니다. 한 글의 접속이나 수정이 실패해도 뒤의 글과 게시판을 계속 확인하며, 남은 대상은 다음 사이클에 다시 확인합니다.

게시 검증 기록과 보강 색인은 기록 파일 크기만으로 처리를 중단하지 않습니다. 기존 첨부 목록도 개수와 관계없이 끝까지 대조합니다. 보강은 이미 확인한 원문·내용 해시와 실제 정보 개선 여부를 기준으로 판단하며, 수정 횟수만으로 중단하는 상한은 없습니다.
